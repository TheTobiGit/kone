## Findings

### 1. [P2] A liveOnly steer becomes a queued turn during a restore and loses its delivery callbacks

Location: **packages/agent-core/src/AgentService.ts:1046–1047**, reached through **2604–2650**. `steerTurn` checks `liveOnly` only in the `isBusy` branch (2627). An idle thread held by a restore has no announced turn and is not busy, so it falls through to `sendTurn`, whose new restore branch durably queues it.

Scenario: an urgent inbox steer was initiated while a turn was live, but that turn finishes before the dispatcher handoff and a checkpoint restore now holds the directory. The caller deliberately supplies `liveOnly:true` so that the steer refuses instead of becoming a queued row. At this pin it resolves with `queued:true`, and the restore's wake later sends the row as a fresh turn. Enqueue does not preserve TurnSendOptions; promotion calls dispatchToAdapter with the queue-settlement hook alone (3147–3151). The original `onSending`/`onAccepted` callbacks are never invoked by this eventual delivery.

This matters to the actual urgent inbox caller at **inboxDelivery.ts:204–230**: its `onAccepted` callback settles the hand-over, and rejection releases/retries it. A queued success does neither, leaving the claimed hand-over without the caller's acceptance settlement even though its words later reach the provider. The old c5ae1d34 restore branch rejected this same handoff, allowing the caller's existing release/retry path to run.

Repro: **/home/gideonsarfo/Developer/kone-wt/reviews/p2-b37b836e-extra-restore-repro.test.ts:347**, test `liveOnly steer must refuse rather than queue during restore`. Uses a real store and holds restoreCheckpoint at its await. No live turn exists; svc.steerTurn with liveOnly resolves instead of rejecting and creates a queued row. The correct refusal assertion fails with an undefined error. Gate release and cleanup run before the assertions, so the test does not leak a claim.

Preserve the liveOnly refusal before falling through to the new restore queue. Ordinary sends can continue to queue behind the restore.

### 2. [P2] Command-based compaction bypasses the restore admission guard

Location: **packages/agent-core/src/AgentService.ts:1368–1378** (new shared send guard), bypassed by **1899–1920 and 1993–1999** (compactThread/runCompaction).

Scenario: an idle thread is already inside a hard checkpoint restore. The caller requests manual compaction. compactThread checks busy but not restoreHolds, and command compaction directly calls `adapter.sendTurn` rather than sendToAdapter. It therefore starts a provider turn during the claimed reset. The new assertion that every turn path ends at the shared guard is false for this path. The busy marker is added only after the restore already owns its claim, so it cannot prevent that already-running reset.

This is a real supported mechanism: ClaudeAdapter.ts:194 advertises `/compact`; CursorAdapter.ts:776 and DroidAdapter.ts:554 advertise `/compress`. The service itself describes command compaction as an ordinary turn at AgentService.ts:1993 and 178. The issue is an admission hole in the existing P2 restore-safety fix; the direct compaction path predates this range, but remains a caller of the service whose admission policy changed here.

Repro: **/home/gideonsarfo/Developer/kone-wt/reviews/p2-b37b836e-extra-restore-repro.test.ts:364**, test `command compaction must not start an adapter turn during restore`. A fake adapter advertises the production command capability; with restoreCheckpoint gated, compactThread sends **["/compact"]**, expected no adapter send. A short injected boundary timeout cleans up compaction; finally releases the restore gate. This proves provider-turn admission during the claim, not actual provider file mutation; no live CLI was run.

Manual compaction must honor the restore claim before starting its command turn, as ordinary sends and Send now now do. Native compaction's internal provider operation was not tested as a file-writing operation here.
